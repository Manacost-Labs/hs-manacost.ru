# Изменения карт в статьях

Блок показывает баланс-патч так: **карта до → стрелка и плашки изменений → карта после**.
Фона, рамки и панели вокруг изменения нет — только карты, стрелка и плашки.
В ряд по умолчанию идут два изменения; можно выбрать один или три. На экранах
до 720 px изменения всегда идут по одному в ряд. Клик (или Enter) по изменению
открывает в лайтбоксе сайта «До» и «После» рядом, крупно.

## Как вставить (для редактора)

1. В Classic Editor нажмите **Изменения карт** рядом с «Добавить медиафайл».
   В блочном редакторе кнопка находится в боковой панели, в блоке «Изменения карт».
2. В поле «Дата и время патча (UTC)» проверьте момент выхода патча. По умолчанию
   подставляется дата публикации статьи. Для нового черновика это «сейчас» —
   тогда изменений ещё нет, поэтому поставьте дату патча.
3. Введите русское название карты (от двух букв). Поиск идёт сразу по Constructed
   и по «Полям сражений»; можно ограничить одним режимом. Нажмите на карту, чтобы
   добавить её в статью. За раз можно вставить до 12 изменений.
4. У каждой добавленной карты видно, какая пара найдена («До — … · После — …»).
   Если для даты пары нет, будет показана текущая карта с плашками; если у карты
   нет архивных изображений или сервис истории не отвечает — только плашки.
5. Плашки считаются автоматически по разнице характеристик. Их можно править:
   изменить «Было»/«Стало», выбрать цвет, убрать плашку, добавить плашку
   (Мана, Атака, Здоровье, Прочность, Броня, Уровень, Текст) или **Свою метку**.
   Для «Полей сражений» плашка «Текст» не считается автоматически — добавьте её
   вручную, если изменился текст. «Пересчитать из истории» вернёт автоматические плашки.
6. Выберите «В ряд» (1, 2 или 3), размер карт и, при желании, подписи «До» и «После»
   (по умолчанию выключены). Предпросмотр справа обновляется сразу.
7. «Вставить изменения» вставит шорткод в выбранное место текста (в блочном редакторе —
   блок «Шорткод»). Отмена обычная, текст статьи при закрытии окна не меняется.

Цвет плашки: зелёный — лучше для игрока (больше атака, здоровье, прочность, броня;
меньше мана), красный — хуже, нейтральный — «Уровень» и текстовые плашки.

## Шорткоды

```text
[hs_card_changes columns="2" size="m" captions="no"]
[hs_card_change card="BE_036" date="2026-11-03 15:55"]
[hs_card_change card="BG36_362" mode="bg" date="2026-11-03 15:55" plates="attack:5:6;~Новый эффект"]
[/hs_card_changes]

[hs_card_change card="BE_285" date="2026-11-03" size="l"]
```

| Атрибут | Где | Значения |
|---|---|---|
| `columns` | контейнер | `1`, `2` (по умолчанию), `3` |
| `size` | контейнер или одиночный | `s`, `m` (по умолчанию), `l` — максимальная ширина карты |
| `captions` | контейнер или одиночный | `no` (по умолчанию), `yes` — подписи «До» и «После» |
| `card` | изменение | идентификатор карты, например `BE_036` |
| `mode` | изменение | `constructed` или `bg`; без атрибута определяется по идентификатору |
| `date` | изменение | `ГГГГ-ММ-ДД` или `ГГГГ-ММ-ДД ЧЧ:ММ`, UTC; без атрибута — дата публикации статьи |
| `name` | изменение | название для подписей; без атрибута берётся из истории карты |
| `plates` | изменение | пусто — автоматически; `none` — без плашек; иначе список через `;` |
| `before`, `after` | изменение | SHA-256 архивных изображений (ставит диалог; закрепляют пару в статье) |

Плашка в `plates`: `ключ:было:стало` с необязательным цветом `|good`, `|bad`, `|neutral`.
Ключи: `mana`, `attack`, `health`, `durability`, `armor` (Constructed), `tier` (Поля сражений),
`text` (без значений). Своя метка: `~Название:было:стало`. Некорректные плашки отбрасываются.
В шорткоде нет символов `<`, `>`, `&`: WordPress (wptexturize) и TinyMCE переписывают их, и атрибуты ломаются.

Диалог записывает `before` и `after`: статья показывает именно найденные карты и не
зависит от сервиса истории. Руками набранный шорткод без них разрешается при показе
страницы (см. ниже). Шорткоды нельзя редактировать в диалоге после вставки —
править значения можно прямо в тексте шорткода или вставить блок заново.

## Источник данных и правила выбора пары

Карты и плашки берутся из публичной истории карт Koloda:
`https://api.kolodahearthstone.com/api/v1/card-history/<entity>/<cardId>`
(`constructed_card` для Constructed, `card` для «Полей сражений»). История ведётся с
11 октября 2026: для более старых патчей «до» нет, и блок показывает текущую карту.
Показываются только неизменяемые архивные изображения `/uploads/card-history-media/<sha256>.png`
(русский рендер 404×558 для Constructed и 256×388 для «Полей сражений»).
Поля `local_image_url` и `local_gold_image_url` не используются: их путь меняется без
реальных изменений карты.

Для даты патча D: **до** — самая новая версия с архивным изображением, замеченная раньше D;
**после** — самая старая версия с архивным изображением, замеченная в D или позже, чьё
изображение отличается от «до». Нет пары — одна текущая карта с плашками, без заглушек.

## Эксплуатация и пределы

- **Просмотр страницы не обращается к API.** Страница читает только кэш. Промах (или устаревший
  короткоживущий результат) отдаётся как есть — текущая карта с плашками либо только плашки — и ставит
  в очередь одно фоновое задание WP-Cron `hs_card_changes_warm` на запись (повтор не ставится 5 минут).
  Задание ставится только из основного запроса одиночной записи; ленты, REST, архивы и виджеты только читают кэш.
  Сохранение записи с неприкреплёнными изменениями тоже лишь ставит это задание.
- Фоновое обновление: таймаут запроса 5 с, до 4 запросов параллельно, общий бюджет 20 с на задание
  (включая догрузку старых страниц истории), ответ не больше 512 КиБ, редиректы не выполняются,
  служебный User-Agent (без него API отвечает 403). Блокировка на карту не даёт двум воркерам грузить
  одну и ту же карту. Учитываются `WP_HTTP_BLOCK_EXTERNAL` и `WP_ACCESSIBLE_HOSTS`, а также фильтр `pre_http_request`.
- Кэш (transient, 30 суток): пара неизменяема и не устаревает; результат без пары свежий 10 минут
  (12 часов, если дата патча старше двух суток: архив уже догнал патч), «нет изображений» — 1 час,
  затем отдаётся устаревшим, пока идёт обновление (stale-while-revalidate).
- Если фоновое обновление изменило данные статьи, вызывается `clean_post_cache()`: WP Rocket сбрасывает
  кэш страницы, и читатели получают картинки без ожидания срока жизни кэша.
- Ошибка API (включая исключение транспорта) запускает cooldown 60 с или `Retry-After` (до 1 часа); в пакете запросов действует самая длинная задержка.
  Во время простоя страница показывается из кэша, а без кэша — с плашками без картинок; фатальных ошибок нет.
- Диалог: только `resolve` обращается к API (не чаще 60 раз в минуту на редактора, ответ 429);
  `compose` (предпросмотр и шорткод) не обращается к API вообще и строится из присланных закреплённых данных
  (не чаще 120 раз в минуту). Предпросмотр рисуется без картинок для карты, у которой нет закреплённой пары.
- На одну запись приходится не больше 24 изменений суммарно (вложенные и одиночные шорткоды).
- Имена файлов ассетов версионируются хешем содержимого (таблица в `render.php`, сверяется тестом).
- Выключатель: константа `HS_CARD_CHANGES_REMOTE_ENABLED = false` в `wp-config.php` отключает
  исходящие запросы; уже закэшированные и закреплённые изменения продолжают показываться.
- Шорткод, набранный вручную без `before`/`after`, на холодном кэше сначала показывается только плашками, пока не отработает фоновое задание; если страницу уже закэшировал кэш страниц, картинки появятся после его очистки. Вставленные через диалог изменения закреплены и от этого не зависят.
- Метрика: хук `hs_card_changes_provider_result` получает только безопасный код исхода.
- Внешних скриптов, шрифтов, cookies, localStorage и новых таблиц нет. Читатели загружают
  изображения карт напрямую с `api.kolodahearthstone.com` (адрес и User-Agent видны этому хосту).
- Поиск по русскому названию идёт в два источника и объединяет результаты: сначала словарь плагина HS Smart Tooltip
  (локально, мгновенно), затем архив карт `api.kolodahearthstone.com` (`/api/v1/constructed-cards?q=` и
  `/api/v1/cards?q=` для «Полей сражений»), который знает карты новее словаря — например, BG36_362
  «Жертвенный страж гнева». Запросы к архиву идут через тот же ограниченный транспорт (таймаут, параллельно по
  режимам, отдельный cooldown поиска, `Retry-After`, выключатель; сбой поиска не останавливает историю карт), результат кэшируется на 10 минут, не больше 40 обращений к
  архиву в минуту на редактора. Миниатюры показываются только с разрешённых хостов и путей: архив —
  `api.kolodahearthstone.com/uploads/`, словарь — хосты изображений HS Smart Tooltip; при сбое или лимите диалог показывает результаты словаря с пометкой. Если не
  нашлось и так, остаётся «Добавить по идентификатору».
- Лайтбокс подключается только на опубликованных записях. В предпросмотре черновика клик
  по изменению открывает изображение карты обычной ссылкой.

## Владение и границы

`wordpress/mu-plugins/hs-card-changes.php` — загрузчик MU-плагина. `pairs.php` — чистые правила
(выбор пары, плашки, грамматика `plates`); `source.php` — клиент API, очередь и cooldown; `cache.php` — кэш, блокировки и проверка формы; `warm.php` — фоновый прогрев и `save_post`; `search.php` — поиск карт (словарь + архив);
`render.php` и `card-changes.css` — шорткоды и разметка; `admin.php`, `dialog.php`, `editor.js`,
`editor.css` — диалог редактора и AJAX. Режим пары в лайтбоксе — часть
`wordpress/mu-plugins/hs-manacost-lightbox/` (`[data-hs-lightbox-pair]`); отдельной
библиотеки просмотра нет.

Доступ к AJAX `wp_ajax_hs_card_changes`: nonce `hs_card_changes` и `edit_post` для редактируемой
записи (post/page). Сервер принимает от браузера только поля из закрытых списков и
значения, проверенные регулярными выражениями; HTML, CSS и произвольные URL не принимаются.
Диалог вставляет только текст шорткода, полученный от сервера. Обработчиков сохранения,
изменений autosave/revisions и очистки кэша нет.

## Проверка

```sh
python3 -m unittest tests.test_card_changes -v
bash ops/integration/card-changes.sh
make check
make contracts
make integration
make visual
```

Юнит-тесты используют записанные ответы API (`tests/fixtures/card-changes/`, патч 37.0.2:
Матриарх, Костоправ, Рыцарь-гибрид, Жертвенный страж гнева) и не обращаются к сети.
Интеграционный сценарий работает в disposable WordPress: Classic Editor и Gutenberg,
права автора/подписчика, nonce, публикация, revision/autosave, разметка на 320–1440 px,
лайтбокс с клавиатуры и `prefers-reduced-motion`. Для снимков с настоящими картами задайте
`CARD_CHANGES_IMAGES` — каталог с файлами `<sha256>.png`; без него используются заглушки.

Контракт внешнего сервиса: `config/integrations/card-changes.json`.

Smoke на staging: `tests/card-changes/staging.mjs` (шаг в workflow «Admin performance staging», использует четыре защищённых секрета staging). Проба входит в админку, открывает «Изменения карт», ищет «Жертвенный страж гнева», вставляет блок 2 в ряд в одноразовую запись, проверяет вывод, картинки и лайтбокс и удаляет запись (даже при ошибке; только `test.hs-manacost.ru`). Лайтбокс не грузится на черновиках и в превью, поэтому запись на время проверки становится приватной (не публичной). Запуск с ветки (не main) не разворачивает ветку на staging: поиск по имени там может быть добавлен по идентификатору (`CARD_CHANGES_NAME_SEARCH=optional`). Откат — обычный revert
релиза: вставленные шорткоды остаются текстом статьи, таблиц и данных вне `post_content` нет.
