# Published articles MCP

User setup, tool examples and the dated delivery status are in
[services/articles-mcp/README.md](../../services/articles-mcp/README.md).

## Contract and current delivery boundary

`services/articles-mcp` is an independent Node 22 service. WordPress is the source;
SQLite FTS5 is a derived, disposable search index. No WordPress plugin, hooks,
editor scripts, DB schema, page counters, media files or PHP-FPM configuration change.
The normal WordPress deployment does **not** install/start this separate service.

Tools are `search(query)`, `fetch(id)`, `list_articles(cursor, limit)` and
`list_categories(page)`. Search/fetch return the citation-compatible JSON text
format, including nonempty `url`. Tool annotations and server implementations are
read-only. No arbitrary URL fetch, SQL, shell, write, settings, users or media API
is available to clients. Documents are reference data, not agent instructions.

Search is Unicode word-prefix AND search, with title weighting. It is not semantic
search or Russian morphological analysis. Search returns at most 20 candidates;
live filtering may yield fewer. Archive traversal uses `next_cursor`, including
on an empty filtered page. Category IDs are returned in article metadata; category
names come from the public WordPress taxonomy API.

## Data boundary and freshness

Anonymous `wp/v2/posts?context=view&status=publish` is the only content source.
Password-protected records are excluded. Drafts/private posts/revisions/users and
private post meta are never requested. Sources are explicitly limited to the
primary `.ru` host and isolated `test` host; an index is permanently source-bound.
The mirror is not a second archive. Adding Koloda requires a separate reviewed
source policy and separate index; this implementation does not combine sites.

The worker first enumerates metadata in pages of 100, then fetches changed bodies
in batches of 25. Pauses are at least 200 ms; each HTTP call has an 8-second timeout,
8 MB response cap and no redirect following. Duplicate IDs, changed total counts,
malformed responses or an incomplete traversal abort reconciliation. Work is
staged in a temporary SQLite table, then committed atomically. Failure preserves
the previous committed index. Initial indexing and full rebuilds should be run
off peak. Run only one sync worker (use `flock` as below).

Changed bodies are selected by `modified_gmt`, with a two-minute overlap against
the last completed sync to catch same-second changes. `sync --full` re-fetches all
bodies, including content generated by updated shortcodes/theme filters without
changing the post modification date. Schedule a full sync daily if those generated
parts must stay current. A search index may lag edits/new posts until the next sync.

Before **every** search/list/fetch result, one bounded metadata request verifies
publication, password protection and the indexed modification date. Stale bodies
are withheld until sync. This uses `_fields=id,modified_gmt,content.protected`:
WordPress 6.9.7 does not call `the_content` for those fields. Requests include
`Cache-Control: no-cache` and a changing query parameter; deployment must verify
that REST metadata is not served from a stale edge cache. Source failures return a
safe tool error; the service does not fall back to unvalidated cached documents.
There is the usual request-time race if publication changes after validation.

Full `content.rendered` is requested by the background worker only. It uses the
site's existing shortcode rendering, so the first release must check representative
Newspaper/deck/gallery articles on staging. Conversion retains headings, links,
tables, code and image URLs; scripts/forms/navigation are removed. Images stay in
S3. The worker does not download or change images. No embedding provider is used.

Derived public text persists until reconciliation or local index retirement.
Protect the DB directory (0700), keep it outside the repository and web root, and
exclude it from Git. The CLI uses umask 0077. Logs contain operational counts only;
never add full article text, queries, access tokens, subjects or credentials.

## Local/STDIO setup

```sh
npm ci --prefix services/articles-mcp --ignore-scripts
export MCP_SOURCE_ORIGIN=https://hs-manacost.ru
export MCP_DATABASE=/absolute/private-directory/articles.sqlite
flock /absolute/private-directory/sync.lock node services/articles-mcp/cli.js sync
node services/articles-mcp/cli.js stdio
```

The operator must create the private directory first. STDIO grants the local
process access; protect the account/configuration that launches it. Configure a
client with command `node`, an absolute path to `cli.js`, argument `stdio`, and the
two environment variables above. Never run sync on the same stdout as STDIO.

For staging use a **different** database and `MCP_SOURCE_ORIGIN=https://test.hs-manacost.ru`.
Supply its HTTP Basic Authorization header in the protected environment variable
`MCP_STAGING_SOURCE_AUTHORIZATION`. This is infrastructure authentication, not a
WordPress account. Staging forwards this header into PHP, where WordPress may
interpret it as an application password and return 401. Verify this interaction
before using a standalone staging configuration. The supplied staging probe
uses `openStagingSource`: an ephemeral browser session with the existing staging
diagnostic account. Reads use browser fetch through the same origin DNS mapping
as the existing admin diagnostic workflow, on its server runner (the hosted runner
cannot reach the origin). Cookies are never exported, and no
REST nonce is sent, keeping REST context anonymous. It closes the
browser after the probe. Use this harness for staging source checks; provision a
separately reviewed staging source connection before operating a persistent
staging service. Production remains anonymous and refuses source credentials.

## Remote HTTP and OAuth

The server listens only on `127.0.0.1:8792`; a reviewed HTTPS reverse proxy must
expose `/mcp` and `/.well-known/oauth-protected-resource/mcp` on the selected host.
Do not expose the listener directly, cache MCP responses, strip Authorization,
relax Wordfence globally or use staging Basic Auth as MCP authorization.
Configure the following values in the service environment:

- `MCP_RESOURCE_URL`: exact HTTPS resource identifier ending in `/mcp`.
- `MCP_OAUTH_ISSUER`: `<source-origin>/mcp-oauth`, exactly matching the access token.
- `MCP_OAUTH_JWKS_URL`: exact `<source-origin>/mcp-oauth/jwks`.
- `MCP_PERMISSIONS_CLIENT_SECRET`: protected secret for the existing Reader
  permissions bridge, selected by source environment. Never put its value in Git.
- `MCP_PORT`: optional loopback port, default 8792.

Articles MCP is the resource server. The authorization server is implemented in
this repository's Reader BFF, reusing Hearthpulse login and current-role checks.
See [the OAuth runbook](mcp-oauth.md) for PKCE/DCR/consent, protected signing keys,
opt-in configuration, schema, proxy templates and release/rollback. No additional
Hearthpulse repository code is needed for this profile.

The user-authorized audience is **current Hearthpulse administrators**, including
accounts signed in through Telegram. Reuse the canonical
`createReaderPermissionsClient` from `services/reader/community-clients.js`:
`/identity/reader-permissions` resolves `users.role=admin` and no `blocked_at` on
**every** authenticated MCP request. No role cache or browser/token role grants
access. Role loss, account blocking or a permissions-provider failure denies the
next request. Preserve this source dependency in the service deployment. The
bridge currently accepts the existing Reader client IDs/secrets; provision its
protected environment explicitly, or extend Hearthpulse for a dedicated MCP
permissions client in a separately reviewed change. Do not invent a new role API.

Require signed JWT **access** tokens (`typ=at+jwt`, RS256), exact site OAuth issuer
`<source-origin>/mcp-oauth`, exact MCP audience, `articles:read`, subject, issue time
and expiry. Maximum accepted age is 15 minutes. ID tokens, opaque tokens and other
sites' issuer/resource/JWKS are rejected by the CLI configuration boundary.

The new authority issues this token profile after existing Hearthpulse login and
explicit admin consent. The official SDK completes discovery/DCR/PKCE/token/read
in local fixtures. Remote production exposure is **not yet enabled**: Reader flags,
private RSA key, separately deployed MCP index/listener and reviewed HTTPS routes
are still required. Telegram credentials remain exclusively with Hearthpulse.
Role removal or provider failure denies the next MCP request. Refresh revocation
or Reader logout stops renewal; existing JWTs may last up to 15 minutes.

Launch with `node services/articles-mcp/cli.js http`. Missing or invalid OAuth
configuration fails startup. Invalid tokens fail with 401 and protected-resource
metadata. Host/Origin checks, 16 KiB request cap, four concurrent tool requests,
60 requests/minute/subject and 300 total requests/minute are enforced. HTTP responses
are `no-store` and `noindex`. Read-only annotations are not an authorization boundary.

## Deployment and verification

1. Pass `make articles-mcp-test`, `make check`, `make code-quality` and secret checks.
2. Push a short branch/PR. Run **Articles MCP staging probe** manually on that ref;
   it uses existing staging HTTP and diagnostic-user secrets, reads at most 20 articles,
   performs five fetch samples through MCP, and emits counts/times only.
3. Deploy the reviewed service separately on staging, with an isolated index and
   identity client, using the staging-verified commit. Start a bounded sync job every
   five minutes, using `flock`, and set process CPU/memory budgets. The normal
   WordPress workflow alone does not perform this service deployment.
4. Verify actual target clients and OAuth redirect/login/revocation, publication
   withdrawal/password protection, source 401/429/5xx, index rebuild and recovery.
   Verify REST cache bypass and representative article text, including long posts.
5. Measure wp-admin open/save five times before/after with the worker active. Do not
   call a five-sample MCP read probe an admin performance measurement.
6. Production exposure remains a separate release: enforce Hearthpulse administrators, enable
   the reviewed local OAuth authority, configure HTTPS routes, obtain release approval, and follow
   the project production workflow/gates. This PR does not expose a production URL.

Disable by stopping the HTTP process and sync scheduler. Roll back the service to
its previous tested release; retain the index until the rollback is verified, or
rebuild into a new private path. WordPress rollback/data restoration is unnecessary
because this service only reads WordPress. Do not delete source articles or S3 data.
