# Технический план: быстрый и стабильный WordPress на текущем сервере

Дата: 2026-09-09. Владелец: Manacost Labs. Статус: выполнение начато.

## 1. Задача и пределы полномочий

Ускорить реальную работу со всеми инструментами WordPress и публичными страницами hs-manacost.ru на существующем сервере. Не покупать хостинг, не переносить проект на другой сервер, не переписывать WordPress/тему. Сначала проверяемые небольшие изменения исходников, затем staging, затем отдельно согласованный production-релиз.

Нельзя считать готовым результат по одному HTTP 200, пустой тестовой базе, перенесённому spinner или общей оценке Lighthouse. Не отключать безопасность, capability/nonce, autosave, revisions, блокировки редактора, S3, рекламу, аналитику или корректную очистку кэша ради показателя скорости.

Работа с ресурсами соседних сервисов ограничивается инвентаризацией и согласованными лимитами конкретных владельцев. Не завершать чужие процессы, не менять учётные записи production и не выполнять тестовые записи в опубликованные статьи. Создание временной привилегированной учётной записи staging согласовывается отдельно. Секреты не включаются в Git, отчёты и команды с открытыми значениями.

## 2. Исходная точка, не обещание текущего состояния

Аудит 8 сентября: POST post.php — 80 запросов, p50 5,373 с, p95 6,311 с. До 09:00 UTC — 28 запросов, p50 5,194 с. Поэтому задержку нельзя целиком объяснить дневной серией OOM. Успешное открытие новой записи: 67 запросов, p50 1,983 с, p95 3,784 с; отдельно один 502 за 126,927 с. При загрузке медиа полный запрос p50 3,637 с, upstream p50 0,570 с: это разные составляющие, не нужно вычитать независимые медианы и называть разницу сетью.

В том же аудите: 10 записей OOM-kill, насыщение PHP-пула 32 процессами, ошибки Redis; 8 721 опубликованная статья и 160 546 вложений; autoload 755 600 байт. Эти числа нужно обновить перед соответствующим этапом, а не считать неизменными. Наличие плагина в slowlog — гипотеза для профилирования, не доказательство причинности.

Проверено 9 сентября в исходниках origin/main 840b30ab2008a12ebf87c20b1e46e02d00609d88:

- staging credential preflight завершается успешно при отсутствующих параметрах доступа, затем замеры и артефакты пропускаются;
- collector исследует четыре экрана и не выполняет POST сохранения;
- dataset_size берётся из переменной окружения, а не из измерения базы;
- interactive_ms основан на DOMInteractive и не доказывает готовность TinyMCE/основного инструмента;
- integration fixture из одной записи проверяет механизм теста, а не production-масштаб.

## 3. Архитектурные решения

1. Сохраняем текущие WordPress, Newspaper/tagDiv и редактор. PHP, БД, браузер и внешние сервисы профилируются раздельно.
2. Источник — Git-репозиторий hs-manacost.ru. Работа в отдельном worktree; /var/www — только цель штатной выкладки.
3. Стенд и изолированные тестовые контейнеры остаются на текущем сервере. Используются собственные имена, volumes, порты и лимиты; тяжёлые прогоны последовательны и останавливаются при давлении на production.
4. Не добавляем второй набор SEO/кэш/медиа/безопасности поверх существующего. Профилировщик — только ограниченный staging-инструмент после проверки совместимости с установленным PHP.
5. Публичный page cache и приватные данные имеют разные правила. wp-admin, login, персональные и авторизованные ответы не попадают в общий HTML-кэш.
6. Изменение схемы, policy хранения данных, runtime-лимитов и выкладка кода — отдельные обратимые задачи. Не смешиваем их в один релиз.

## 4. Целевые показатели

Это предварительные цели следующего этапа, а не достигнутые показатели и не автоматическое изменение утверждённых CI budgets.

| Путь | Цель | Условия |
|---|---|---|
| Открытие списка/обычного инструмента | Основной элемент доступен за 1–1,5 с | Прогретое состояние, фиксированные роль/данные/сеть |
| Редактор | Готовность TinyMCE и кнопок до 2 с | Отдельные cold/warm прогоны |
| Сохранение обычной статьи | p50 <=1 с; p95 <=1,5 с | Данные действительно записаны; draft/update/publish отдельно |
| Поиск/фильтры медиа и статей | p95 <=700 мс | Пагинация, реалистичный объём |
| Небольшое AJAX-действие | p95 <=500 мс | Права/nonce проверены |
| Autosave | p95 <=800 мс | Без потери данных и конфликтов двух редакторов |
| Публичный интерфейс | LCP <=2,5 с, INP <=200 мс, CLS <=0,1 | p75, desktop/mobile отдельно, без имитации рекламных показов |
| Надёжность | Нет OOM и устойчивого насыщения PHP при согласованной нагрузке | Интервал включает пики, а не только снимок после reboot |

Минимум 5 сопоставимых прогонов на вариант для предварительной медианы; для p95 использовать более широкую выборку (целевой ориентир >=100 операций) и явно указывать n. Ошибки/тайм-ауты сохранять отдельными счётчиками, а не исключать из отчёта об успешности. Не объединять разные роли, типы операций и сетевые профили в одну оценку.

## 5. План задач и зависимости

В каждой задаче владелец, evidence и фактический rollback уточняются до первого изменения. Размер S — 1–2 файла, M — 3–5; более крупную работу делить на самостоятельные изменения.

### Этап A — достоверность измерений

#### A1. Прекратить ложный зелёный результат staging (S)

- Область: .github/workflows/admin-performance-staging.yml, tests/test_admin_performance_automation.py.
- Отсутствие хотя бы одной из четырёх защищённых настроек должно завершать preflight ненулевым кодом. Проверять это исполнением реального shell-фрагмента workflow с синтетическими значениями, не только поиском строки exit.
- Полный набор параметров разрешает дальнейшие шаги, но не называется успешным замером. Никакие значения не выводятся. Пустой набор артефактов не считается успехом.
- Credentials доступны только preflight и collector; установка зависимостей следует за preflight и выполняется с --ignore-scripts. Проверяется отдельным regression-тестом.
- Проверка: red/green regression, make check, actionlint, secret scan, независимый review. Production и настройки GitHub не меняются этим патчем.
- Откат: отдельный revert workflow/test; не откатывает и не изменяет данные сайта.
- Зависимости: нет. Статус: исходники и тесты готовы, финальный make check и независимый review прошли. Workflow не активирован: feature-ветка не объединена в main.

#### A2. Подтвердить тестовую идентичность и доступ (S)

- Область: protected staging environment и одноимённый тестовый WordPress, не production.
- После согласования использовать существующую или временную отдельную учётную запись; не использовать сессии редакторов. Не обходить Basic Auth/WAF.
- Зафиксировать способ безопасной передачи параметров в runner, ограничить срок действия и удалять только собственную тестовую учётную запись по проверенному ID.
- Проверка: вход в staging, отказ неверным credentials, отсутствие секретов в артефактах. Отсутствующий доступ — BLOCKED, не PASS.
- Зависимости: A1; отдельное подтверждение привилегированного тестового аккаунта.

#### A3. Подтвердить объём и идентичность стенда (M)

- Область: ops/performance, staging-only performance probe, тесты; контракт расширять отдельным изменением.
- Собирать агрегаты количества статей, вложений, пользователей и наиболее крупных таблиц; никаких содержимых/PII. Подтверждать environment и версию развёрнутого кода.
- dataset_size из env считать ожиданием, а не фактом. Ошибка при несовпадении/неподтверждённом наборе; не подменять реальную выборку произвольным 1000.
- Репрезентативный dataset создавать из синтетических/обезличенных данных ограниченными батчами в изолированной БД. Не импортировать production-секреты, письма, токены, webhook-конфигурацию.
- Проверка: mismatch, wrong environment, пустая база, достаточный объём, повторный запуск, отсутствие внешних сообщений и рекламы.
- Зависимости: A2, B1, C1; rollback удаляет только собственные fixtures/volume, не общий staging-контент.

#### A4. Измерить готовность интерфейса и состав отчёта (M)

- Область: collect-admin-performance.mjs, builder, budgets, tests; отдельная версия evidence при несовместимых изменениях.
- Заменить proxy DOMInteractive на наблюдаемую готовность главного контрола. Разделить навигацию, SQL/HTTP/PHP, long tasks, bytes, ошибки и фактические условия запуска.
- Требовать полный набор четырёх экранов, уникальный run-id и чистую собственную output-directory; исключить повторное использование старых артефактов. Различать PASS/BLOCKED/FAILED/NOT_MEASURED.
- Четыре экрана — только исходный минимум. После получения доступа составить матрицу фактического меню: статьи/редактор, медиа, рубрики/метки, пользователи, настройки, SEO, кэш, безопасность, S3 и собственные инструменты Manacost. Для каждого определить отдельные открытие/поиск/основное действие; замеры только четырёх экранов не называть проверкой всех инструментов. Опасные действия security/cache/backup не запускать на production ради теста.
- Проверка: отсутствующий/дублирующийся экран, stale evidence, timeout, неверная роль, изменившийся deployment SHA, secret rejection.
- Зависимости: A3. Откат: согласованная пара collector/builder, не смешивать схемы.

#### A5. Добавить сценарии сохранения (M на один сценарий)

- Область: новый scoped staging/integration journey в ops/performance, disposable fixtures и тесты.
- Отдельные сценарии: новый draft, update published, autosave, preview, publish, revision restore. Свои fixtures маркировать и удалять по точному manifest, не по широкому фильтру.
- Измерять ответ на POST и подтверждённую сохранность post_content/метаданных; 302 не равно доказательству правильного содержимого.
- Проверка: повторный запрос, двойное нажатие, два редактора, ошибка сети, устаревший nonce, отказ прав. Ошибочное «Сохранено» недопустимо.
- Зависимости: A2–A4. Нагрузочные записи в production запрещены.

### Контрольная точка A

Пять сопоставимых начальных samples на каждый экран, достаточная выборка действий, подтверждённые данные/роль/версия и реальные save-сценарии. До этого нельзя заявлять, что WordPress ускорен.

### Этап B — надёжность общего сервера

#### B1. Обновить карту ресурсов и задать бюджет тестам (S)

- Снять current/previous boot OOM, PSI, swap, PHP queue/max_children, медленные запросы, временные файлы и cgroup-потребление без секретов.
- Найти владельцев тяжёлых процессов; не считать OOM-жертву виновником. Сопоставить интервалы нагрузки с запросами WordPress.
- Для собственных тестов определить concurrency=1, лимиты CPU/RAM/PIDs, бюджет диска, timeout и условия прекращения теста. Не запускать общий make integration вслепую при нехватке ресурсов.
- Проверка: сериализованный пробный прогон и отсутствие роста production-ошибок/очереди. Зависимости: нет.

#### B2. Ограничить согласованные вспомогательные нагрузки (M на сервис)

- После B1 подготовить конкретные systemd/docker limits с резервом для production; не убивать процессы и не менять глобальные user.slice по предположению.
- PHP pool считать по measured per-worker memory и конкурентности; Redis лимит/eviction обсуждать с владельцами всех использующих его приложений. maxmemory-policy нельзя менять, считая Redis исключительно кэшем WordPress.
- Проверка: конфиг-тест, один сервис за раз, контролируемая нагрузка, 24–72 часа наблюдения с пиками. Откат: предыдущая named config для этого сервиса.
- Зависимости: B1, согласование затронутых соседних workloads.

#### B3. Настроить оповещения и эксплуатационный сценарий (M)

- Использовать существующий мониторинг: OOM, swap/PSI, PHP очередь/5xx, Redis connectivity, SQL locks, age фоновой задачи, disk/inodes и свежесть restore-check.
- Разделить WordPress, Plausible, media proxy и views-counter; общий nginx error count не должен называться частотой ошибок редактора.
- Проверка: безопасный synthetic alert без аварии production, маршрут уведомления, инструкция восстановления. Зависимости: B1.

### Этап C — восстановление и редакторские данные

#### C1. Восстановить из бэкапа в изолированную цель (M)

- Найти актуальные backup manifests core/media и независимость копий. Проверка /etc/hostname не считается WordPress restore.
- На текущем хосте выделить изолированную БД/директорию/лимиты; отключить реальные письма, webhooks, рекламу и cron-мутации внешних систем.
- Проверить импорт БД, login, статьи, media URLs/объекты, оригиналы и sidecars; измерить RPO/RTO. Никаких восстановлений поверх production.
- Зависимости: B1 и достаточный запас диска; отдельный target manifest и cleanup собственных объектов.

#### C2. Восстановить политику revisions/retention (S/M)

- Установить, почему в аудите было только три revision; проверить фактические настройки и обработчики, не обвинять неактивное расписание WP Rocket.
- Согласовать сохраняемую историю и тест восстановления длинной статьи с колодами. Не чистить revisions до определения политики.
- Зависимости: C1, A5; проверка: content hash и подтверждённый rollback редакторского изменения.

### Этап D — ускорение главных действий

#### D1. Найти владельца пяти секунд сохранения (M)

- На staging профилировать PHP bootstrap, save hooks, SQL/locks, внешние HTTP, cache purge и очередь. Доказать вклад по одному request, а не вычитанием агрегированных медиан.
- Сначала существующая телеметрия; временный profiler только с ограничением overhead и без SQL values/cookies/post bodies в отчёте.
- Проверка: трасса реального POST с подтверждённым воспроизведением и один dominant bottleneck. AIOSEO/Wordfence/purge — кандидаты, не предрешённый диагноз.
- Зависимости: A5, B1; не включать SAVEQUERIES/Xdebug на production.

#### D2. Исправить подтверждённую причину сохранения (M на причину)

- Возможные решения выбираются только по D1: bounded query/index; устранение N+1; caching стабильного вычисления; исключение неуместного обработчика; ограничение внешнего HTTP.
- Вторичные задачи можно вынести в durable queue с idempotency key, retries/backoff, пределом попыток и наблюдаемым failed state. Запись основного контента/критичных метаданных не подменять очередью.
- Cache purge: адресная инвалидизация после commit, правильная зависимость article/list/home, без stale/private leakage и глобального FLUSHDB как привычного действия.
- Проверка: regression до изменения, before/after, отказ очереди/Redis/HTTP, сохранение и публикация во всех регионах; rollback учитывает уже поставленные задачи.
- Зависимости: D1, C1, A5; каждый owner отдельным patch.

#### D3. Ускорить открытие редактора и dashboard (M на экран)

- Измерить metabox/панели/виджеты и повторные запросы. Подключать assets и вычисления только на владеющем screen; lazy-load необязательные панели без потери функций.
- Не отключать Heartbeat полностью; сохранить autosave, lock и восстановление сессии. Не вводить глобальный React/admin rewrite.
- Проверка: editor/admin/denied role, primary-control readiness, keyboard/mobile, cold/warm, ненарушенный post_content.
- Зависимости: A4, B1; файлы выбираются из трассы, не по размеру плагина.

#### D4. Ускорить списки, поиск и медиатеку (M на экран)

- Серверная пагинация, выбор только необходимых полей, debounce и отмена/игнорирование устаревших ответов; bounded SQL и indices по EXPLAIN.
- Раздельные сценарии: media grid/list, поиск имени, фильтры дат/автора, выбор изображения в редакторе, bulk actions.
- Проверка: большой dataset, последняя страница, пустой результат, одинаковые имена, права на приватные вложения, ошибка/повтор.
- Зависимости: A3–A4, C1 перед schema-изменениями.

#### D5. Ускорить загрузку и обработку медиа (M на стадию)

- Сопоставить body ingress/buffering, upstream, создание размеров, оптимизацию, S3 и insertion отдельно. Разные размеры файлов/сети не смешивать.
- Проверить существующие deferred subsizes/optimizer workers, повторные попытки, контроль ошибок и размер очереди.
- Оригиналы неизменны; новые форматы — sidecars. Исключить конкурирующую двойную оптимизацию и гонку одинаковых имён.
- Проверка: MIME/hash/dimensions, upload retry, S3 timeout/recovery, вставка/preview, обе proxy routes.
- Зависимости: A5, C1; не добавлять новый optimizer без подтверждённого пробела.

### Этап E — база, кэш и публичный интерфейс

#### E1. Уменьшить ненужную работу с options и событиями (M)

- Проверить зависимости крупных autoload-options, частоту использования и invalidation. Не переводить настройки темы массово в no-autoload.
- Для event tables согласовать retention и агрегаты: индексы под реальный запрос, ограниченные батчи архивации, сохранение бизнес-счётчиков.
- Проверка: before/after query plan/latency/rows, границы даты и повтор батча, восстановление. Размер таблицы сам по себе не доказательство проблемы.
- Зависимости: C1, D1/D4 evidence.

#### E2. Проверить согласованность всех слоёв кэша (M)

- Составить ownership: browser, edge, WP Rocket, object cache. Проверить HTTP headers, cache key, авторизацию, cookies, invalidation и ограниченный прогрев.
- Не начинать с purge-all. Не объединять настройки кэширования публичных и персональных страниц.
- Проверка: статья сразу после обновления, новый комментарий/счётчик, гость/пользователь, origin/Москва/Новосибирск; зеркало .com остаётся noindex.
- Зависимости: A4, D2 для cache-related fixes.

#### E3. Сократить вес страницы без поломки РСЯ (M на ресурс)

- Приоритет: крупная статья-картинка, корректный srcset/sizes, размеры thumbnail и карточек, fonts, CSS/JS duplication.
- Главное изображение не откладывать до прокрутки; нижние медиа загружать по необходимости. Резервировать место без огромных пустых блоков.
- Яндекс-loader один раз, уникальные slot IDs и независимые состояния; timeout/no-fill/adblock не трактовать как гарантированный сбой показа.
