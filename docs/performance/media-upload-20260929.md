# Проверка загрузки изображений — 29 сентября 2026

## Статус инцидента

Пользователь сообщил об ошибке обработки любого изображения на
`hs-manacost.ru` и `kolodahearthstone.com`, затем подтвердил: «работает».
Первоначальный отказ воспроизвести не удалось. Его причина **не установлена**.
Нельзя считать сообщение WordPress о 2560 пикселях доказательством нехватки RAM:
установленный core показывает его также при общем HTTP_ERROR загрузчика.

Оба домена проверены через обычный вход и загрузчик браузера, собственными
временными пользователями с `upload_files`. Это две отдельные установки WP.

| Проверка | Результат |
| --- | --- |
| hs-manacost.ru, PNG 1800×1200 | HTTP 200, 768 мс |
| kolodahearthstone.com, тот же PNG | HTTP 200, 497 мс |
| Удаление production-проб | Оба вложения и обе временные учётные записи удалены |
| Свободная RAM во время диагностики | Около 38 ГБ из 64 ГБ |
| Связанные PHP fatal/OOM в просмотренных журналах | Не обнаружены |

Это отдельные успешные загрузки, не статистическое доказательство устранения
периодического сбоя. Production-код, лимиты PHP и защита в этой проверке не менялись.
Наблюдавшиеся таймауты S3 относились к чтению ранее загруженных изображений;
связь с первоначальным отказом загрузки не подтверждена.

## Восстановление диагностики staging

1. Клонированный триггер `hsmanaco_stage.deleteusers` имел production-definer,
   который не мог выполнить триггер на staging. Создание проверочного пользователя
   завершалось ошибкой `TRIGGER command denied`.
2. Только на staging definer заменён на `hs_stage_wp@localhost`; выдан `TRIGGER`
   только на `hsmanaco_stage.wp_ksoo_users`. Событие BEFORE INSERT и тело
   существующего триггера сохранены. Production-триггер не изменялся.
3. SQL для отката сохранён вне Git:
   `/var/tmp/hs-media-probe-20260929/trigger-backup/rollback.sql`.
   Он восстанавливает прежний definer и отменяет добавленное разрешение.
4. Для CI создан отдельный administrator только на staging. Новые environment
   secrets: `STAGING_DIAGNOSTIC_USER`, `STAGING_DIAGNOSTIC_PASSWORD`.
   Исходные `STAGING_WP_ADMIN_*` сохранены; пара `STAGING_HTTP_*` не менялась.
5. В браузере подтверждена причина остановки автоматического входа: штатная
   страница `confirm_admin_email`. Общий helper нажимает nonce-защищённую ссылку
   «Напомнить позже» только на точном staging-origin. Подтверждение правильности
   email и отключение проверки не используются. Это исправление диагностики,
   не установленная причина пользовательского инцидента.

После обновления staging из production-базы необходимо снова проверить definer
триггера и существование диагностической учётной записи. Если база её утратила,
создать новую через WordPress API только на staging и обновить два новых секрета
через stdin. Пароли, cookies и nonce не сохранять в отчётах или репозитории.

## Автоматическая проверка изображений

`ops/performance/diagnose-media-upload.mjs` запускается в workflow
`Admin performance staging` после замеров экранов и сохранения статьи, в том числе
если один из предыдущих диагностических шагов завершился ошибкой.

- Разрешён только `https://test.hs-manacost.ru` с необязательным завершающим `/`.
  Production, HTTP, URL с логином, параметрами или другим путём отклоняются
  до запуска браузера. Все четыре секрета обязательны.
- Пять последовательных загрузок контролируемого PNG 2048×1024 через настоящий
  `media-new.php`. Каждая получает уникальное имя; повторы POST отсутствуют.
- Проверяются HTTP-ответ, собственный attachment ID/author/title/имя файла,
  исходные размеры и SHA256, MIME, доступность и декодирование миниатюры.
- В `finally` удаляются только вложения текущего запуска и текущего пользователя,
  проверяется ответ удаления и последующий 404. Поиск по случайному префиксу
  помогает найти вложение при потерянном ответе загрузчика. При таймауте POST
  очистка не считается доказанной: обработка на сервере может ещё продолжаться.
- Выгружается JSON без ответов сервера, cookies, nonce и паролей. При ошибке
  сохранён этап отказа и безопасное имя проверки. Не прошедшая очистка также
  делает job неуспешным. Принудительное завершение runner требует ручной проверки
  вложений по `fixture_prefix` из отчёта.

Подтверждённый ручной запуск полного сценария: **516, 492, 506, 506, 521 мс**,
все пять исходников и миниатюр проверены, все пять вложений удалены.
Эта staging-проверка не является самостоятельным доказательством удаления
production-файлов с SSD или выгрузки в S3: staging использует изолированную медиатеку.

сопоставление точного HTTP-ответа неудачной загрузки с журналами PHP, origin и proxy.
