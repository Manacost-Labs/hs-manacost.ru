## Что изменено

`Manacost_Cache_Purge` раньше вызывал один полный набор очисток и для изменений
контента, и для deployment. Кандидат исключает только сброс PHP OPcache для
зарезервированных источников событий статей: `content_`, `updated_`, `status_`,
`after_update_`, `after_publish_`, `delete_` после префикса `auto:`.

Эти префиксы являются внутренними именами событий контента, а не произвольными
именами операций. Изменения PHP/конфигурации должны использовать `ci_deploy`
или другой источник за пределами этих префиксов. Ручная, плановая очистка,
`ci_deploy`, `menu`, `theme` и прочие семейства источников сохраняют полный
сброс. Контракт не обещает полный сброс для произвольной строки, которая
использует зарезервированный префикс.

Очистка WP Rocket, локальных файлов кэша, object cache, reverse proxy и
Cloudflare не изменена. Не менялись права, nonce, autosave, revisions, S3,
реклама, контент или личный кабинет. Удалённый из большого класса шаг OPcache
вынесен в небольшой helper; размер исходного класса уменьшился.

Это устранение лишней операции, а не доказанная причина задержки сохранения.
Согласно [документации PHP](https://www.php.net/manual/en/function.opcache-reset.php),
сброс OPcache требует повторной загрузки и разбора скриптов при последующих
обращениях. Реальный эффект зависит от того, где выполняется очистка: CLI
замер не подтверждает состояние OPcache PHP-FPM.

## Ограничения полноценного допуска и следующие действия

1. На постоянном staging около 8709 опубликованных статей и 160078 вложений.
   Создание новой тестовой учётной записи заблокировал DB trigger `deleteusers`:
   ошибка TRIGGER permission. Триггер копирует новую запись в служебную таблицу.
   Привилегии не повышались, trigger не изменялся, чужие учётные записи и сессии
   не использовались. Нужен рабочий тестовый вход либо отдельно согласованное
   исправление этого препятствия.
2. Пробный CLI draft-профиль без валидной учётной записи исключён из замеров
   админки. Внешний HTTP и почта были заблокированы на время диагностической
   команды; собственные fixture-пост и пользователь отсутствуют после cleanup.
3. Перед продолжением нужно воспроизвести полный авторизованный сценарий
   draft/save/autosave/revision/preview/publish с реальным объёмом данных,
   не менее 5 сопоставимых проб, отдельно SQL/hooks/HTTP и cold/warm.
4. Устранить существующий WPCS-долг затронутого класса отдельным проверяемым
   изменением, не ослабляя gate и не смешивая с изменениями интерфейса.
5. Штатный full-tree deployment из текущего main затронет несвязанные изменения
   reader/account/comments, отличающиеся от production. Требуется согласованный
   состав изолированного выпуска. Полная выкладка не запускалась.
6. Для обычного полного выпуска сохраняется маршрут: проверенный staging SHA →
   production promotion → основной домен/зеркало/origin/оба RU-прокси → реальные
   редакторские замеры. Прямое разрешение пользователя применено только к
   ограниченной двухфайловой правке ниже, не к несвязанным изменениям main.

## Прямая установка на production

Перед активацией проведена новая независимая проверка Astra в свежем контексте:
код, текущий production diff, installer, FPM probe и результаты репетиции отката.
Блокирующих замечаний к этой ограниченной установке не осталось. Reviewer
отдельно сохранил статус FAIL для старого WPCS-долга и ограничения проверки
реального сохранения. Обычный CI gate не объявлялся зелёным и не ослаблялся.

## Откат и границы

Точная резервная копия, installer и манифесты:
`/var/backups/hs-manacost-deploy/20260909-opcache-AViAUP/` (root-only 0700).
`original.php` содержит исходный основной файл с сохранёнными metadata.
Замена и возврат файла отрепетированы в private fixture; исходные SHA256,
owner/group и mode после восстановления совпали. Production rollback не
выполнялся и не выдаётся за выполненный restore-drill всего сайта.

Точечный откат:

```bash
sudo bash /var/backups/hs-manacost-deploy/20260909-opcache-AViAUP/deploy.sh rollback
```

Скрипт проверяет ожидаемые hashes и атомарно возвращает только основной файл.
Helper сохраняется инертным для уже выполняющихся/закэшированных запросов с
новым основным файлом. После отката необходимо дождаться revalidation и
подтвердить 0 параметров `purge_all` в FPM, затем повторить smoke. При drift
не повторять установку/откат вслепую. БД и несвязанные reader-файлы не трогать.
