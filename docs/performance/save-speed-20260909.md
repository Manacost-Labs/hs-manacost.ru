# Ускорение WordPress: первый кандидат и ограничения выпуска

Дата: 2026-09-09 UTC. Ветка: `perf/wp-admin-save-20260909`.
База: `9188a1eb6c03f1b60957bd402978f3f24f6c7b2c`.

## Статус

Кандидат реализован в исходниках и проверен локально. **Не установлен на
production и на постоянный staging; не допущен к выпуску.** Ускорение реального
сохранения статей не доказано. Полный технический план остаётся отдельной
работой в ветке `perf/wp-admin-speed-20260909` (commit `741524c`).

## Что изменено

`Manacost_Cache_Purge` раньше вызывал один полный набор очисток и для изменений
контента, и для deployment. Кандидат исключает только сброс PHP OPcache для
зарезервированных источников событий статей: `content_`, `updated_`, `status_`,
`after_update_`, `after_publish_`, `delete_` после префикса `auto:`.

Эти префиксы являются внутренними именами событий контента, а не произвольными
именами операций. Изменения PHP/конфигурации должны использовать `ci_deploy`
или другой источник за пределами этих префиксов. Ручная, плановая очистка,
`ci_deploy`, `menu`, `theme` и прочие семейства источников сохраняют полный
сброс. Контракт не обещает полный сброс для произвольной строки, которая
использует зарезервированный префикс.

Очистка WP Rocket, локальных файлов кэша, object cache, reverse proxy и
Cloudflare не изменена. Не менялись права, nonce, autosave, revisions, S3,
реклама, контент или личный кабинет. Удалённый из большого класса шаг OPcache
вынесен в небольшой helper; размер исходного класса уменьшился.

Это устранение лишней операции, а не доказанная причина задержки сохранения.
Согласно [документации PHP](https://www.php.net/manual/en/function.opcache-reset.php),
сброс OPcache требует повторной загрузки и разбора скриптов при последующих
обращениях. Реальный эффект зависит от того, где выполняется очистка: CLI
замер не подтверждает состояние OPcache PHP-FPM.

## Наблюдения на действующем сайте

За 24 часа до 2026-09-09 20:43 UTC: 7 запросов POST `post.php`, медиана 1894 мс,
максимум 5202 мс; все ответы 302. Маленькая выборка и редирект не доказывают
корректность сохранённого содержимого. GET редактора: 11 ответов 200,
медиана 862 мс, p95 1313 мс. Старую медиану сохранения 5373 мс из аудита
8 сентября нельзя использовать как сопоставимый baseline этой правки.

## Проверки

- Регрессионный тест исполняет настоящий PHP-модуль с подменой только внешних
  эффектов. До правки 10 проверок сброса OPcache падали. После правки проходят
  3 метода / 15 сценариев: lifecycle статей, страниц и custom post type,
  deployment/default/unknown/scheduled/manual, продолжение очистки Cloudflare
  после ошибки reverse proxy. Проверяется также сохранение остальных очисток.
- `make check`: PASS, 134 Python + 80 Node + 22 reader UI теста, синтаксис PHP,
  контракты, shell/workflow checks. Первая попытка остановилась на устаревших
  номерах строк в манифесте; `make contracts` обновил только номера строк.
- `make integration` на исходной версии: PASS. `make admin-performance` до
  и после правки: PASS; он также запускает integration assertions.
- PHPCompatibilityWP для обоих PHP-файлов: PASS. PHPStan всего first-party
  surface: PASS. WPCS нового helper и проверка размеров файлов: PASS.
- `make code-quality`: **FAIL**. Исходный большой модуль имел 224 ошибки WPCS
  и 38 предупреждений до изменений; после — 223 и 38. Правила и baseline не
  ослаблялись. Это остаётся блокером полноценного допуска.
- Независимая проверка Astra: замечание об именах источников устранено
  явным контрактом; блокирующих замечаний к ограниченному diff не осталось.
  Производственный выпуск reviewer не одобрил из-за перечисленных ограничений.
- Сетевой smoke постоянного staging: PASS. Это проверка доступности текущего
  staging, а не подтверждение установки кандидата или входа в редактор.

Одинаковая роль administrator, desktop 1440; по 5 навигаций на экран в каждом

проверены мобильная геометрия 390 px, перенаправление анонимного посетителя на

## Блокеры выпуска и следующие действия

1. На постоянном staging около 8709 опубликованных статей и 160078 вложений.
   Создание новой тестовой учётной записи заблокировал DB trigger `deleteusers`:
   ошибка TRIGGER permission. Триггер копирует новую запись в служебную таблицу.
   Привилегии не повышались, trigger не изменялся, чужие учётные записи и сессии
   не использовались. Нужен рабочий тестовый вход либо отдельно согласованное
   исправление этого препятствия.
2. Пробный CLI draft-профиль без валидной учётной записи исключён из замеров
   админки. Внешний HTTP и почта были заблокированы на время диагностической
   команды; собственные fixture-пост и пользователь отсутствуют после cleanup.
3. Перед продолжением нужно воспроизвести полный авторизованный сценарий
   draft/save/autosave/revision/preview/publish с реальным объёмом данных,
   не менее 5 сопоставимых проб, отдельно SQL/hooks/HTTP и cold/warm.
4. Устранить существующий WPCS-долг затронутого класса отдельным проверяемым
   изменением, не ослабляя gate и не смешивая с изменениями интерфейса.
5. Штатный full-tree deployment из текущего main затронет несвязанные изменения
   reader/account/comments, отличающиеся от production. Требуется согласованный
   состав изолированного выпуска. Полная выкладка не запускалась.
6. После снятия блокеров: проверенный staging SHA → production promotion →
   основной домен/зеркало/origin/оба RU-прокси → реальные редакторские замеры.

## Откат и границы

До выпуска откат runtime не требуется: сайт не менялся. Будущий релиз обязан
доставлять основной MU-файл и helper вместе; отсутствие helper вызовет fatal.
Откат — предыдущий согласованный комплект этих файлов через штатный процесс,
без восстановления всей production БД. Нельзя выкладывать или откатывать
несвязанные reader-файлы в рамках этой оптимизации.

Профиль: WordPress. Метод: проектные Admin Performance / Runtime Stack /
Observability, baseline TDD/review/security/Git и Release Manager. Расширенный
набор навыков обусловлен обязательным project baseline; типографика и UI-код
не менялись. Рабочая копия основной reader-задачи сохранена без изменений.
